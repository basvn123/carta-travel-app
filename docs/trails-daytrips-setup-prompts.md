# Trails + daytrips vertical: setup prompts

Source: research doc "Building a Europe-Wide Travel App on Free/Open Data" (validated 2026-08-06).
Each prompt below is meant to be pasted into a fresh Claude Code session from the repo root.
Dependency order: 1 -> 2 -> (3, 5, 6, 7 in any order) -> 4 -> 8 -> 13 -> 9 -> 10 -> 11 -> 12.
Prompt 13 (city trips) only needs 1 and 7; it can run before the hiking prompts if cities are the priority.

Adaptations vs the research doc (why some recommendations were changed):
- No Prefect / n8n: the repo already has run_pipeline.py with cadence tiers and a Windows scheduled task. Extend it.
- No Supabase PostGIS: the live project (ntssxktaduxzpsmejwyv) has a zero-billing posture and must never receive db pushes. The content store is a local Docker PostGIS; published output ships as static JSON like the rest of the app.
- Copernicus GLO-30 only for elevation: SRTM stops at 60N, which cuts off most of Norway, Finland and Iceland.
- Pilot with 4 countries (CH, FR, NO, AT) before scaling to 44.

---

## Prompt 1: Content-lab PostGIS foundation

Create a local staging environment for a new trails and daytrips content vertical. Add tools/trailslab/docker-compose.yml running a PostGIS image with pgRouting (for example the pgrouting/pgrouting image), port 5433 to avoid clashes, plus an init SQL migration creating: trips (id, country, category hike/daytrip, title, geom geometry(MultiLineStringZ,4326), distance_m, ascent_m, descent_m, duration_min, difficulty, sac_scale, network, source, source_ref, license, attribution_text, status enum draft/needs_review/approved/published/rejected, quality_score numeric, raw_tags jsonb, gap_info jsonb, created_at, updated_at, last_validated_at), trip_stops (trip_id, seq, poi_ref, dwell_min, leg_mode, leg_duration_min, leg_geom), images (subject_type, subject_id, url, title, author, source_url, license, attribution_text, is_approved; reject NC/ND at insert), validation_runs (subject_type, subject_id, check_name, passed, score, details jsonb, run_at), portal_trails (country, name, geom, source, license), data_sources (name, license, attribution_template, last_refreshed_at, refresh_cadence). GiST indexes on all geometry columns. Add pipeline/trails/db.py (psycopg) reading connection settings via the pipeline/env_local.py pattern. Add rows to docs/tos/data_licenses.md for the planned sources: OSM (ODbL), Copernicus GLO-30, swisstopo, IGN BD TOPO (Etalab 2.0), Kartverket Turrutebasen (CC BY 4.0). This DB is local-only; never touch the live Supabase project. Acceptance: docker compose up succeeds, migration applies, a Python smoke test inserts and reads back a trip with 3D geometry.

## Prompt 2: Hiking route ingestion from Geofabrik extracts

Build pipeline/trails/ingest_osm_routes.py. Download per-country Geofabrik .osm.pbf extracts (start with switzerland, france, norway, austria) into data/raw/geofabrik/ with a manifest, following the conventions of the src/ingestion collectors. Using pyosmium, extract relations with type=route or superroute and route=hiking/foot/walking, assemble member ways into an ordered MultiLineString, and store into the trips staging table (source=osm, source_ref=relation id, license=ODbL) with tags preserved in raw_tags (name, ref, network, osmc:symbol, osmc:status, sac_scale, distance, roundtrip). Do NOT bulk-query the public Overpass API. First-pass filter: network in iwn/nwn/rwn, or the relation has a name. Record member gap count and unordered-member issues into gap_info for the later continuity check. Handle missing members and duplicate ways gracefully. Acceptance: per-country ingest counts logged; spot-check that famous routes appear (Via Alpina stages for CH, at least one GR for FR).

## Prompt 3: Elevation layer (Copernicus GLO-30)

Build pipeline/trails/elevation.py to sample a DEM along staged trip geometries and fill distance_m, ascent_m, descent_m, max grade, plus a downsampled elevation profile stored in raw_tags or a profile jsonb column. Use Copernicus GLO-30 (30 m, global, free with attribution): fetch only the COG tiles covering the pilot countries from the public AWS bucket (copernicus-dem-30m) into data/raw/dem/, sample with rasterio (bilinear). Do not use SRTM: it stops at 60N and misses most of Norway and Finland. Handle nodata and sea-level zeros at coastlines. Apply a smoothing window plus a minimum climb threshold before accumulating ascent, since raw 30 m sampling badly overstates ascent on noisy terrain. Compute a duration estimate with a documented hiking-time rule (DIN 33466 or Naismith with Langmuir corrections; pick one and note it in code). Acceptance: run on the ingested Swiss routes and print name, km, ascent; sanity-check one Via Alpina stage against known figures.

## Prompt 4: Validation engine

Build pipeline/trails/validate.py writing to validation_runs and computing quality_score (0-100) per staged trip. Checks: (a) continuity: reassemble member ways, detect gaps above a 50 m tolerance, count disconnected components, use the osmc:status tag as a signal; (b) geometry sanity: nonzero length, no jumps above 2 km, bbox inside the claimed country; (c) elevation sanity: recomputed distance within 25 percent of any distance tag, average grade below 45 percent, ascent plausible for the distance; (d) difficulty: derive from distance + ascent + sac_scale, flag contradictions; (e) completeness: name, network, description present. Weights live in a config dict. Auto-set status: needs_review above a threshold, rejected below a floor, never auto-approve. Every check writes its own validation_runs row with details jsonb. Acceptance: run over all pilot routes, print the score distribution and top 20 per country.

## Prompt 5: National portal cross-check

Build pipeline/trails/crosscheck_portals.py. Load three official trail datasets into the portal_trails staging table: swisstopo swissTLM3D hiking trails (attribution: swisstopo), IGN BD TOPO path network for France (Licence Ouverte Etalab 2.0), Kartverket Turrutebasen for Norway (CC BY 4.0; available as GML, FGDB, GPX or WFS). Then match staged OSM trips to official geometry: accent-folded name similarity plus geometric proximity (ST_DWithin buffers or Hausdorff distance), write a portal_agreement check into validation_runs, boost quality_score on agreement, flag length or location mismatches. Mind the repo gotcha that accent folding must handle l-with-stroke and friends (see the POI dedupe folding logic in continent-app for the approach). Add or update source rows in docs/tos/data_licenses.md. Acceptance: agreement rate printed per country plus a sample of confirmed matches with distances.

## Prompt 6: Popularity signals + seed shortlists

Reuse existing popularity infrastructure to rank staged trips for curation. The repo already has pipeline/harvest_pageviews.py (Wikipedia pageviews) and a sitelink fame proxy in the OSM/Wikidata harvester. Build pipeline/trails/popularity.py: for each staged trip, resolve anchor entities (wikipedia/wikidata tags on the relation itself, else famous summits or POIs from the existing catalogue within 2 km of the line), attach sitelink counts and pageviews, then compute curation_rank blending network level (iwn above nwn above rwn), portal agreement, quality_score and popularity. Output per-country seed shortlists (top 15) as CSV under data/reports/trails_seed/. Acceptance: shortlists exist for CH, FR, NO, AT and famous routes rank near the top.

## Prompt 7: Self-hosted Valhalla + gap repair

Stand up local routing to repair gappy hike geometries and later compose daytrip legs. Add tools/trailslab/valhalla/ with a docker compose for a maintained Valhalla image, building tiles from the per-country Geofabrik extracts already cached under data/raw/geofabrik/. Per-country tiles only; do not build a full Europe graph on this machine. Then build pipeline/trails/repair.py: for trips failing the continuity check, route between gap endpoints with pedestrian costing, splice the repaired segment, store the repaired geometry alongside the original with repaired=true and the length divergence percent. Divergence above 15 percent flags for human review instead of auto-accepting. Acceptance: one gappy route repaired end to end, before and after lengths printed, and re-running validation shows the continuity check passing.

## Prompt 8: Daytrip composer

Build pipeline/trails/compose_daytrips.py deriving daytrip products from existing catalogue data plus staged hikes. Input: an anchor dest id from the continent-app catalogue; pick its top POIs (existing items and ratings), optionally one nearby approved hike under 4 hours, and sequence them with a simple time-budget solver (greedy nearest neighbour honouring opening hours and dwell times; mirror the dwell assumptions already in the continent-app day planner). Legs: walking and driving via the local Valhalla, transit via the Transitous plan API reusing the client patterns in tools/reachability/build_reach.py (including its IncompleteRead retry and coordinate-dedupe gotchas). Store results as trips rows (category=daytrip) with trip_stops. Acceptance: compose 3 pilot daytrips (for example Interlaken, Chamonix, Bergen) and print the itineraries with leg times.

## Prompt 13: City trip composer

Build pipeline/trails/compose_citytrips.py deriving curated one-day city sightseeing trips from the existing catalogue, as first-class trip products alongside hikes and daytrips. City selection must be based on actual market demand, not the app's internal fame signals. First build pipeline/trails/market_demand.py: harvest official tourism statistics into a market_demand table (city, country, latest annual visitor nights, year, source, license). Primary source: Eurostat urban audit culture and tourism data (urb_ctour, nights spent in tourist accommodation per city, open license) plus its country-level tour_occ series for context. Where city coverage is thin for a pilot country, fall back to the national statistics office open data: BFS HESTA for Switzerland, INSEE for France, SSB for Norway, Statistik Austria for Austria. Do not scrape commercial rankings (Tripadvisor, GetYourGuide and similar are ToS-closed like AllTrails). Add a row per source to docs/tos/data_licenses.md. Then per pilot country pick the top cities by visitor nights, using the app's rating_v2 and fame signals only as a tiebreaker or for cities the statistics do not cover, and log which basis picked each city. Per city: take the top rated POIs (existing items with images and descriptions; require an acceptable image license and coordinates, drop POIs failing that), cluster to the largest walkable area the way the plan-day walking budget does, sequence into a realistic day with the dwell-time assumptions already used by the continent-app day planner, and compute walking legs via the local Valhalla (fallback: straight-line distance at 4.5 km/h if Valhalla tiles for that country are not built yet). Store as trips rows (category=citytrip, geom nullable or the walking line) with trip_stops referencing catalogue POI ids. Validation (reuse validate.py where possible, add citytrip checks): every stop has name, coordinates inside the city region, an approved-license image and a description; total walking under a configurable budget; day length between 5 and 9 hours; popularity floor on the city itself. Then the same gates as everything else: needs_review, human approval in the review UI (prompt 10), grounded description via describe.py (prompt 9), export via export_wire.py (prompt 12) with category included so the app can render city trips as their own shelf. Acceptance: market_demand populated with sourced visitor-night figures for the pilot countries; compose city trips for the top 5 demand-ranked cities per pilot country, print the demand ranking with its source next to each itinerary, and confirm the trips land in needs_review with validation_runs rows.

## Prompt 9: Grounded descriptions via Claude

Build pipeline/trails/describe.py generating short descriptions for staged trips, using the Claude API strictly as a rewriter over supplied facts. Load the claude-api skill first to pick the current model and SDK usage. Per trip, build a facts block: name, type, country, distance, ascent, duration, difficulty, network, portal confirmation, nearby anchor entities, and a Wikivoyage snippet as signal only (never copy its prose; it is CC BY-SA). Prompt constraints: use only supplied facts, no new numbers or claims, no em or en dashes, output 2 summary sentences plus one short paragraph. Then run a verification pass asking the model to map every sentence to a source field, dropping sentences that do not map. Store description_md and a described_at stamp. API key via the pipeline/env_local.py pattern. Acceptance: descriptions generated for the Swiss seed shortlist with a spot check for fact drift.

## Prompt 10: Local review UI + publish gate

Build a local-only admin app for reviewing staged trips. tools/trailslab/review/: small Vite + React app (load the carta-design skill first and follow it), backed by a tiny local API (FastAPI or Express) that talks only to the local PostGIS and binds 127.0.0.1. Queue of needs_review trips showing: MapLibre map with the trip geometry (guard NaN coords the way src/map/coords.js does), an elevation profile chart, computed metrics vs source tags, all validation_runs results, portal agreement, and the generated description in an editable textarea. Buttons: Approve, Reject, Save edits. Approve is the only path to status=approved; nothing auto-publishes. Nothing here touches the live Supabase project. Acceptance: review one Swiss route end to end and see its status flip in the DB.

## Prompt 11: Orchestration + freshness (extend run_pipeline)

Wire the trails pipeline into the existing orchestrator; do not add Prefect or n8n. Extend run_pipeline.py at the repo root, following its existing task registration and cadence-tier pattern, with: trails_ingest (quarterly), trails_elevation (after geometry changes), trails_validate (after ingest), trails_popularity (monthly). Add a regression path: when re-validation of a published trip drops below threshold, record it in the freshness report (freshness_report.json pattern) and demote the trip to needs_review; never silently unpublish or delete. Acceptance: run_pipeline --list shows the new tasks and a dry run executes trails_validate against staging.

## Prompt 12: App export + attribution footer

Export approved content as produced works into the app. Build pipeline/trails/export_wire.py writing continent-app/public/trails/{country}.json with published trips only: id, name, category, summary, distance, ascent, duration, difficulty, and a simplified geometry (Douglas-Peucker), plus per-item attribution_text and source. Full-resolution geometry is served per trip on demand only; never ship a bulk raw OSM-derived database, which keeps us in ODbL produced-work territory. Repo gotcha: a missing JSON under public/ returns SPA-fallback HTML with status 200, so check content-type when fetching. Then finish the pending attribution footer pass: continent-app/src/lib/attribution.js exists from the license-ledger chunk; render credits (OpenStreetMap contributors, swisstopo, IGN/Etalab, Kartverket, Copernicus DEM) in the app footer per the carta-design skill. Update the status column in docs/tos/data_licenses.md for sources now live. Acceptance: country JSON files exist and the footer shows the credits.
